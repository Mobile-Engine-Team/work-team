成员、角色与邀请

很多团队刚开始用 Loop 时，会把“工作区管理”理解成“接机器、建智能体、调配置”。

这些当然重要，但如果成员、角色和邀请路径本身没讲清楚，后面的协作很容易一开始就混乱。

先看三种基础角色

当前用户最需要记住的工作区角色只有三种：

owner
admin
member

这是团队日常管理最稳定、最实用的心智模型。

owner 负责什么

可以把 owner 理解成这个工作区的最终负责人。

当前最重要的职责包括：

管理工作区设置
管理成员
管理机器
管理智能体
决定谁是 admin、谁是普通 member

如果团队里有需要明确拍板的人，通常就是 owner。

admin 负责什么

admin 更接近“日常运营这个工作区的管理员”。

它通常可以负责：

管理智能体
管理机器
管理大部分日常成员运营动作

但 admin 不是所有私有频道的后门入口。私有频道的可见性和治理仍然是频道内的。

更适合由 owner 保持最终控制的事情，例如成员角色变更，仍然应该按 owner 视角来理解。

简单说：admin 帮团队把系统跑顺，但不是工作区最终主权的替代者。

member 负责什么

member 是日常协作的默认参与角色。

它更适合做这些事：

在频道、DM、话题中协作
使用 @智能体
创建和跟进任务
在 #all 中协作、加入公开频道、或被邀请进入私有频道

member 不是管理员角色，不负责工作区结构治理。

智能体在成员语义里是什么

这点很容易被误解。

智能体当然会以成员身份参与协作，但它不是工作区管理角色。

更稳妥的理解是：

智能体是协作参与者
智能体不是 owner
智能体也不是拿来替代管理员的工作区管理主体

所以涉及成员治理、角色治理、机器治理的动作，默认都还是人类管理员的职责。

Invite 流程怎么理解

当前最实用的理解方式是：

owner 或 admin 输入已注册且完成验证的 Loop 账号邮箱或手机号并发送邀请
被邀请人使用该账号登录
查看并明确接受待处理邀请
使用匹配且已验证的身份进入目标工作区
系统将其加入该工作区所属组织，并为其建立工作区成员身份
新成员默认进入正常协作路径

对于已有且已验证的账号，Loop 会确认邀请已发送，并将待处理邀请提供给被邀请人。对方在线时，站内邀请提示会立即刷新；离线时，下次登录仍会看到邀请。被邀请人必须明确接受后才会加入工作区。邀请链接仅作为已创建待处理邀请的兼容入口保留。

被邀请人也可以打开工作区设置，在“收到的待处理工作区邀请”版块中集中查看所有尚未处理的工作区邀请。表格会显示工作区和邀请人，并提供接受或拒绝邀请的操作。

再次邀请同一个目标时，Loop 会刷新已有待处理邀请的过期时间，不会新增邀请记录，但每次明确的邀请操作仍会发送一次实时刷新信号。如果对方已经是该工作区的 active 成员，Loop 会提示“该用户已加入此工作区”，且不会发送邀请通知。

没有配置 OAuth provider 的部署，在工作区 Members 页面提供两个明确的成员 操作，并分别打开独立的 Dialog：

邀请成员：保留上面的已验证账号邀请流程。
创建成员账号：填写邮箱或手机号、用户名和可选的显示名称，在当前组织和工作区中创建本地账号，并显示一次性的初始密码。邮箱和手机号至少填写一个，不发送邮件或短信验证。对方首次登录时必须修改密码。初始密码不会由 Loop 发送，Dialog 关闭后也不会再次显示；在 Dialog 中默认掩码显示，可通过显隐按钮临时查看。 对方可以使用填写的邮箱或手机号，以及初始密码登录。历史用户名登录仍保留用于兼容。

启用 OAuth 后，邀请成员可以填写邮箱或手机号，并生成可复制的邀请链接。由于本地密码无法用于 OAuth 登录，创建成员账号不会显示。邀请流程不会创建本地密码，不会调用 OAuth provider 的用户管理接口，也不会为对方创建组织或工作区。对方使用 OAuth 登录后，Loop 创建或查找对应的 Loop 账号，校验 OAuth 返回的、与邀请目标对应的已验证邮箱或手机号，再把账号加入邀请人的现有组织和工作区，并直接进入目标工作区。如果 OAuth 身份未验证或与邀请目标不匹配，系统会拒绝加入，并允许对方切换账号或完成验证后重试。

从组织添加是独立的操作：它只授予已有组织成员访问当前工作区的权限，不属于邀请成员或创建成员账号的 Dialog。

这条路径的重点不是“发一次通知”本身，而是让加入工作区这件事有清晰、可审计的入口。

新成员加入后通常会经历什么

一个新成员进入工作区后，最常见的路径是：

先进入 #all
了解团队的频道结构
学会什么时候发普通消息、什么时候 @智能体
对需要持续跟进的事项建立任务

所以 invite 只是开始，不是 onboarding 的全部。

#all 和普通频道的区别

用户最应该记住的是：

#all 是所有成员都会在的默认协作面
普通频道更适合按用途拆分协作上下文
普通频道默认 private，不会自动出现在所有人的列表中
公开频道可以被整个工作区搜索并加入，但在真正加入前不会进入“我的频道”
在加入公开频道前，只能看到基础信息，看不到消息历史
工作区角色与频道 Owner 的区别

工作区角色和频道 owner 有关联，但不是同一个概念。

工作区角色决定谁治理整个工作区
每个普通频道都有自己的频道 owner
已加入成员仍然可以邀请其他人进入该频道
频道 owner 负责设置、移除成员、删除频道和 ownership 转移
即使是工作区 owner/admin，只要没有加入，也不会自动看到私有频道

管理得好的团队，不会把所有长期协作都堆在一个频道里。

什么时候该让谁做什么

一个实用分工方式通常是：

owner：确定边界和关键治理决策
admin：保证工作区每天跑得顺
member：在清晰规则下专注协作本身

如果这三层长期混在一起，团队会很难判断：

谁来接新成员
谁来调整机器和智能体
谁来定义频道结构
谁来决定角色和权限变化
常见误解
误解一：只要能协作，就不需要管角色

不是。

越是开始接入更多成员、更多机器、更多智能体，越需要把角色讲清楚。

误解二：智能体也可以当管理员

不应该这样理解。

智能体是协作角色，不是工作区主体治理角色。

误解三：invite 完成就等于 onboarding 完成

不是。

邀请只是把人带进工作区，真正决定体验的是后续的协作规则、频道结构和角色边界。
