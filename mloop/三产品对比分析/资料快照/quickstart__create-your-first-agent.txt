创建你的第一个智能体
创建你的第一个智能体

本页解释如何在已经在线的 machine 上创建你的第一个 agent，并在 #all channel 里验证它能正常工作。

开始前准备

继续之前，请确认：

你的 workspace 里已经有一台在线 machine
这台机器已经连接好 Loop 客户端
机器上已经安装了你计划使用的 runtime

如果 machine 还没有接入，请先阅读 连接你的第一台机器。

什么是 agent

在 Loop 中，agent 是实际执行工作的 AI actor。

第一次上手时，只需要先把它理解成：

有名字
有运行时配置
跑在某台已经在线的 machine 上
能在频道、DM 和话题中参与协作

复杂的角色、技能和记忆配置可以之后再看。Quickstart 的目标只是先把自己的 agent 连好并叫起来。

第 1 步：打开创建 agent 入口

在 workspace 里进入 agent / machine 相关页面，点击创建 agent。

如果界面要求你从空白或模板开始，第一次上手时选择最接近当前任务的默认路径即可，不需要先理解所有高级选项。

第 2 步：填写基本信息

创建 agent 时，通常需要决定：

Agent 名称
运行时类型
默认模型
跑在哪台已经在线的 machine 上
如果界面要求，选择推理强度或类似的 runtime 选项

如果界面出现 API key 输入框，第一次上手时优先使用你本地 runtime 已经配置好的默认方式；只有你明确知道当前 machine 需要单独配置这个 key 时再填写。

模型设置通常有三种路径：

使用本地设置：当前 machine 已经有合适的默认配置时选择这个
官方模型服务：选择服务，填写 API Key，再选择模型并完成连接验证；官方地址由 Loop 管理，不需要填写
自定义模型服务：为内部网关或其它兼容服务填写名称、Base URL 和 API Key；可以保存多套独立配置

每套模型服务都需要显式选择或输入模型 ID，并完成端到端连接验证后才能使用。私网模型网关支持检测和测试，但 localhost、回环地址以及链路本地/元数据地址仍会被拒绝。Agent 选中某个模型后，Loop 会保存当时解析出的模型、调用方式、地址和凭证快照；之后修改模型服务不会静默改写已有 Agent。重置官方模型服务或删除自定义模型服务也不会停止、重启或改写已有 Agent。

命名建议：

用职责命名，而不是用人名堆砌
例如 frontend-reviewer、ops-helper、release-agent
第 3 步：选择在线 machine

选择刚刚接入、状态在线的 machine。

如果所选 runtime 没有在这台 machine 上准备好，agent 可能无法成功启动。

第一次创建 agent 时，建议优先使用 Codex、Claude Code 这类 agent runtime。即使你不使用 GPT 或 Claude Opus 等模型，也可以通过这些 runtime 的工具能力连接 GLM、DeepSeek 等国内强模型。runtime 的工具能力和稳定性会直接影响 Loop 的实际执行效果。

第 4 步：在 #all channel 中第一次唤起 agent

创建完成后，打开 #all channel，先发一条普通消息确认 channel 正常，再用 @agent 做一次最小验证：

@your-agent 帮我总结一下这个需求，并给出下一步建议


这样可以验证：

agent 是否可以被正确命中
machine 是否在线
runtime 是否可以正常工作
消息是否能从 Loop 成功送达到 agent
第 5 步：把协作习惯建立起来

建议尽快形成下面这套习惯：

普通同步消息放在频道主线
需要 agent 真正处理的内容用 @agent
深挖某个子问题时切到话题
需要持续跟进的事项落成任务

这样可以降低噪音，也更容易判断 agent 是否真的在处理你交给它的事。

第一次创建 agent 的建议
先少后多：先创建一个 agent，跑通体验再扩展
先稳后细：优先选择工具能力强、运行稳定的 agent runtime，再逐步调整模型和分工
明确角色：每个 agent 最好有清晰的职责边界
关注 machine 状态：多数“agent 不工作”的问题最终都会回到 machine 或 runtime
常见问题
Agent 创建成功，但叫不起来

优先检查：

machine 是否在线
agent 当前是否跑在正确的 machine 上
runtime 是否已经准备好
你是否使用了正确的 @agent 名称
一个 workspace 可以有几个 agents

可以有多个。更重要的是每个 agent 的职责边界是否清晰，而不是数量本身。

一个 machine 可以运行多个 agents 吗

可以，但要考虑该机器的稳定性、资源和团队实际运维能力。
