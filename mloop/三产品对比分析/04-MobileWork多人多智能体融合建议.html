MobileWork 融合建议：共享责任、受控执行、证据验收

建议把 MobileWork 扩展为“人对结果负责、Agent 在授权环境中执行、团队按证据验收”的协作产品。保留个人桌面任务，在其上增加共享工作主线。

建议

本篇所有新增对象、默认规则、阶段和验收项都是建议，尚未实现。用户提供的团队原型与 v0.2 技术方案仅作为设计输入，原型 localStorage 演示不证明生产能力。

03 / 建议用户心智：一件事，多个人，多次执行

对王蕾，系统应回答“问题是否已被证据证明修好”；对周启明，应回答“我负责什么、Agent 现在改哪一版”；对陈晓，应回答“我测了什么、结果绑定哪一版、失败交回谁”。三者都围绕 W17，而不是到处寻找散落的聊天。

一眼读懂工作卡片：W17「弱网重复待办」｜责任人 周启明｜执行 修复助手｜状态 待评审｜最新产物 v2｜QA2 通过｜待 王蕾验收。点击任一字段能反查来源，而不是只显示一个笼统“完成”。

04 / 建议对象模型与模块关系

对象最小字段关系与约束
TeamWorkspaceid、组织名、成员、保留策略有 1:N Project；与 LocalWorkspace 无等号关系
Projectid、目标、visibility、成员、资料版本有 1:N WorkItem；有显式团队参与范围
WorkItemid、projectId、humanOwner、executorRef、status、priority、version、acceptanceCriteria人类责任始终明确；1:N Run / Thread / ReviewRequest
Comment / Threadid、rootId、replyToId、author、body、editedAt、deletedAt、version、attachments同根回复；消息可见性继承工作项；编辑不偷偷重跑
AgentInstanceid、assetVersion、owner、accessPolicy、runtimeBinding、capabilities专家资产可复用；实例调用权限和机器授权分离
DispatchCommand / RunidempotencyKey、expectedVersion；runId、triggerRef、agentId、runtimeId、inputSnapshot、status、cost命令去重；一次 Run 一份执行记录；用户消息队列不充当台账
ArtifactVersionartifactId、versionId、hash/commit、sourceRunId、storageRef、visibility内容和来源不可变；改动创建新版本，不覆盖旧批准
TestEvidenceid、artifactVersion、caseVersion、environment、expected、actual、result、logRef包含通过/失败与实际验证范围；不因一句“已测”生成通过
ReviewRequest / Decisionreviewer、workItemVersion、artifactVersions、testEvidenceIds；actor、result、reason、timestamp决策不可改写；通过只对指定证据有效，新版本需重新批准
Subscription / AuditEvent对象、用户、通知偏好；actor、action、targetVersion、result直接提及单独处理；关注、已读与 Agent 执行分开

两套状态机必须分离

层次建议状态转换规则
WorkItem 业务层todo → in_progress → in_review → done；blocked / cancelled 分支开始由显式派工或人确认；提交评审要求版本与证据；返工回 in_progress；done 要求有效 Decision
Run 执行层queued → dispatched → running → completed / failed / cancelled；cancel_requested 为中间事实执行完成只更新 Run 与产物；不直接验收 WorkItem；取消请求需要执行端确认
ReviewRequest 决策层pending → approved / rework / rejected / superseded批准绑定证据版本；新版本令旧请求过期；不能把点赞/工具许可当批准

05 / 评论与回复：默认意图必须可预测

推荐默认“仅留言”。在输入区旁提供独立的“请求执行”，显示这次给谁、基于哪份上下文、是在本轮后执行还是停止后重启。用户能在发送前看到实际后果。

微功能建议规则边界与错误处理
发送文本/附件默认“仅留言”；草稿与失败重试保留提交前展示可见范围；附件单独检查权限与配额
回复某人保存 rootId 与 replyToId；仍留在同一顶层讨论不会因回复 Agent 就默认执行；主动点击“请求执行”
提及人使用真实身份候选，触发通知不改变负责人、状态或执行者；避免作者自通知
提及 Agent / 小队选择后展示“仅提及 / 请求执行”与权限状态执行才创建派工命令；P0 小队仅协调 Agent 可受控派成员
编辑评论作者可改，显示编辑标记并保留版本不自动重跑旧请求；新增通知可预览，重跑需新命令
删除评论作者删除；管理员管理删除留原因与审计根评论留占位，回复与已用执行快照按保留策略留存；不能删掉合法证据链
重复/并发提交客户端稳定命令键；服务端原子去重与版本校验同一键不同内容拒绝；发现远端更新让用户选合并或重新提交
表情回应同一人同表情开/关，仅记录反应不唤醒、不变负责人、不代替通过
解决/重开讨论标记讨论已解决；新回复可重开并提示讨论解决与 WorkItem done、Decision approved 独立
批注与结论 P1选区快照、编号、草稿；同讨论一个选定结论新结论替换需留历史；引用内提及不触发；限制容量以压测确定
只留言/执行预览明确本次通知人、Agent、权限、忙闲与预计资源不能只用颜色表示；无权目标不可静默略过
运行中补充P0 仅“本轮后开始”或“停止后重新执行”仅在引擎能证明送达时 P1 开放无中断插话，保留回执
通知与订阅项目/工作项订阅，直接提及，分配、失败和待验收去重取消关注不取消直接提及；已读只影响人的注意力，不影响执行
评论转子项 P1选定评论及此前必要上下文生成来源快照不自动带出无权内容；子项责任/权限单独确认，后续源更新提示而不覆盖

06 / 权限、上下文与并行边界

边界建议规则
谁能看项目成员资格 + 工作项可见性 + 附件访问共同约束；服务端校验，不靠隐藏按钮；管理员可治理但不自动阅读全部私有内容
谁能调用 AgentAgent owner 决定调用 Access；项目有权不自动有 Agent 调用权；派工前校验模型、机器与预算
谁能批准安全许可由机器/会话有权人做；业务通过由指定评审人做；Agent 可以给建议，P0 不替人类验收
哪些上下文共享项目资料、工作项说明、选择的评论快照与授权文件引用；个人记忆、私聊、连接器密钥默认不共享
团队资产如何复用把个人专家/技能以明确版本复制或引用为团队实例；作者发布和调用方授权分开，撤销后禁止新调用
如何并行P0 同一可写目录串行；独立目录或 worktree 可并行，但共享浏览器、外部账号与发布资源仍需锁或人工协调
何时自动停止预算、工具次数、总时长、委派深度、相互唤醒次数分别设上限；超限暂停并保留账本，默认阈值由试点校准
离线与恢复控制面记录真实确认状态；取消不承诺立即远端终止；重连核对 runId、输入版本、权限版本与幂等键后回交
保留与删除UI 软删除与证据快照保留分别定义；按组织策略期限与合法删除请求实际清理，不能永久保留一切
失败补偿已发生外部写入按工具能力提示人工评估或补偿；不宣称统一事务或全副作用回滚

09 / 分期实施与进入下一阶段的门槛

阶段内容放行标准取舍
P0 · 跑通一条可信闭环团队成员与最小权限；项目/工作项；评论/回复/真实提及；显式派工；指定 runtime；Run/目录锁；产物版本；QA证据；人工验收；通知审计用弱网缺陷案例完成 R1 失败 → R2 通过；刷新/重连不丢责任与证据；越权与重复执行可阻止使用已有专家/技能/工具引擎；不先做全功能聊天、不开放自治跨机器调度
P1 · 降低跨人协作成本线程批注与结论；状态交接模板；Agent 小队受控派工；可送达插话；可保存视图；显式频道回源；个人任务升格工作项并发编辑、来源快照、权限撤销和人工接管均可解释；能完成两个独立项目试点有稳定 P0 证据对象和授权接口之后扩展；每项单独确认接入工具能力
P2 · 在约束内扩大自动化可视化工作流；定时与事件触发；更多运行适配器；模板与运营分析；条件满足后目录隔离并行与人工确认机器迁移预算、异常暂停、循环限制、恢复流程和历史兼容通过试点避免直接复用旧定时任务作为多租户调度器；引入前先做迁移与兼容验证

实现路径：先验证适配契约，再决定复用深度

建议团队协调服务新增持久工作账本，MobileWork 现有引擎通过适配层领取/回报 Run。现有 Session 作为执行载体，不能直接暴露成多人事项。旧自动化继续跑个人任务；团队定时触发通过同一派工命令进入新服务。

Multica 可作为机制参考或独立控制面的候选，但本次没有核验可嵌入 SDK、许可证适配、数据迁移和稳定外部接口覆盖。先用隔离测试项目验证：创建工作项 → 绑定指定 runtime → 回报产物 → 取消确认 → 权限撤销；验证后再决定独立集成、代码复用或自建。不要把已有 HTTP API 等同可替换 MobileWork 引擎。[M_api]

现有本地原型应如何升级

保留王蕾/周启明/陈晓、弱网问题、v1 失败与 v2 通过的贯穿演示。但把 localStorage 事件迁到服务端持久对象，补真实身份、权限、并发控制、版本化产物、机器回报与不可变决策。原型中的“点击完成”只能验收交互连贯性，不能验收真实多 Agent 调度。[P_prototype][P_steps]

10 / 可验证的 P0 验收清单

场景操作应观察到的结果
重复派工同一评论命令连续提交或网络重传只产生一个 Run；同键不同内容拒绝，界面能定位原 Run
明确责任同时 @修复与测试，但负责人未改人类责任人不被提及覆盖；执行者与责任人分别展示
普通回复陈晓在任务内只补一句测试条件保存评论并通知有权成员；不创建 Run、不消耗执行预算
并发状态更新王蕾验收时周启明已提交 v3旧 expectedVersion 或证据集不匹配，不能把 v2 批准扩展到 v3
成员撤权移除原本可执行的成员新派单被拒；活动运行显示请求取消/未确认/已停止，结果保留审计
目录竞争两个 Agent 请求同时修改同一共享目录后者等待或拒绝，不出现无锁双写；独立目录并行需明确隔离
QA 不通过v1 测试实际 2、预期 1留下不可变失败证据，不能 done；返工生成后续 Run
版本验收v2 + QA2 通过后提交人工通过只有指定有权评审者创建 Decision；Decision 可反查输入、版本、测试与执行
机器离线已入队任务绑定机器断联显示等待/失败及原因；不暗中发到另一台机器；恢复有幂等与原版本检查
停止与迟到结果停止后机器迟到回报成功不自动覆盖已停止或新工作状态；仍可查看已发生副作用与历史产物
隐私个人会话含私有记忆、密钥或无权附件团队上下文仅装配被授权快照；密钥不入评论/提示词/共享日志
刷新与恢复P0 场景中途关闭客户端再进入工作项、Run、产物、测试与决策由服务端持续恢复；内存消息队列不当作持久调度

试点指标：先建基线，再设目标

指标口径用于判断
闭环完成率有明确验收 Decision 的已完成工作项 ÷ 试点进入执行的工作项团队是否真正交付，而非只增长消息数
错误执行率用户申诉或取消为“本不想启动”的 Run ÷ 全部 Run显式派工是否减少意图误判
首轮通过率 / 返工率首次候选产物验收通过占比；按版本/原因统计返工多 Agent 是否提高质量，避免以运行数代替效果
等待分解从需求到派工、排队、执行、待人评审分别计时瓶颈是人、机器还是上下文缺失
