01 · 推荐路线

复用协作机制，经 Provider 适配接入完整 Agent 产品

内部预研以 Multica 的完整协作后端和执行端（daemon）为起点。daemon 通过统一的 Provider 适配层，调用各个完整 Agent 产品的 CLI 或可编程入口：Mobile Coder、MobileWork 办公 Agent，以及 Codex、Claude Code 这类第三方产品。MobileWork 同时提供团队协作入口。近期复用的是 Multica 的具体实现，长期稳定的是我们自己定义的接口与职责。暂不先拆出一个新的引擎仓库。
许可前提：只限内部原型范围。Multica License 由 Apache 2.0 与 Part I 附加条件共同构成，两者冲突时以附加条件为准，所以不能当作普通 Apache 2.0 项目直接商用。附加条件规定：单一组织内部使用不需要商业授权；对第三方托管或嵌入商用需要商业授权；UI 品牌和非 UI 归因要分别满足。本轮没有做法务结论。M01 详见第 12 章。

Agent 产品继续负责在一次运行之内把事做完，Mobile Coder 和 MobileWork 内部都消费同一来源的 SDK harness（运行循环、会话、上下文、工具）。新增的协作能力负责跨人、跨运行、跨执行环境推进工作：安排什么、由谁承接、依据是什么、结果交到哪里、什么时候需要人来决定。

为什么接“产品”，不直接接 SDK

Mobile Coder 对标的是 Codex、Claude Code 这类完整 Agent 产品：产品身份、供模、业务插件和宿主装配在产品里，SDK 只提供通用执行机制。C01 让 daemon 调用产品入口，团队执行和个人使用的是同一个产品，产品也能在团队场景里继续被使用和打磨；只套一层 SDK 壳，得到的不是完整的 Mobile Coder 或 MobileWork。

Provider 是什么，不是什么

Provider 是执行端里的调用适配代码：把统一的执行请求翻译成某个产品的 CLI 调用，再把它的输出翻译回统一的事件和终态。它不是 Agent 本体，也不是模型厂商意义上的 provider。Multica 已有统一 Backend 接口和按 runtime/协议族构建后端的机制M05M25M26，本轮未核实已有可直接使用的 MC/MW 适配器。

这条路线成立的三个前提

① 内部原型范围

② 唯一的工作项记录

02 · 现状

有协作机制，但没有可以直接拿走的纯引擎包

Multica 有可复用的引擎机制，包括统一的 Backend 适配接口。但本次阅读没有发现一个与其产品模型完全分离、可以直接安装替换的通用协作引擎交付物，本轮也未核实已有可直接使用的 Mobile Coder / MobileWork 适配器。这不妨碍整体复用，只是说明“把 engine 目录拿出来”这个计划不成立。

Multica

已核实：工作项、Agent/Runtime、运行队列、原子领取、并发限制、条件唤醒、运行结果回执。M06–M16 执行端有统一 Backend 接口，按 runtime/协议族构建后端。M05M25M26

不能由此推出：已有独立发布的通用引擎；可以任意跨机无损恢复；企业知识治理已经完整；已经存在 MC/MW 的 Backend。

mobile-coder-sdk（产品内部的 harness）

已核实：独立 engine 包和 HTTP 客户端；会话分派、工具与权限、运行内 workflow 与子 Agent、本机 Worker。S01–S12

不能由此推出：本机多进程等于跨团队、跨设备的持久编排；SDK 本身就是完整的 Mobile Coder 产品。

Mobile Coder 产品

已核实：仓库约定产品负责身份、供模、业务插件与宿主装配，SDK 负责通用执行机制，vendor 是消费制品。C01 CLI 声明了 run、--session/--continue、--format json、--attach、--dir 等参数C02，run handler 依赖 SDK 引擎C04，开发脚本从平级 SDK 仓库取打包源C03。

不能由此推出：CLI 的取消、审批、事件与终态语义已满足团队执行；本归档与 SDK/MW 基线是已验收的配套版本。

MobileWork

已核实：个人工作区与会话入口；宿主负责启动和管理引擎；本地/远端连接；桌面 OIDC 身份与账号目录。W01–W09

可编程执行入口：orchestrator CLI 的帮助里能看到服务、工作区、文件、审批等命令W13；本轮没有核实一个可由 daemon 调用的完整办公任务执行 CLI，标为待补齐/待验证。

不能由此推出：远端连接就是端云协同调度；本地账号目录就是组织权限。session-message-queue 是录屏 legacy 回执迁移，不是任务调度器。W08

耦合在哪：中间是可复用的运行机制，三根“系绳”把它拴在 Multica 产品模型上。

① 服务依赖

TaskService 依赖工单状态、通知 inbox、归因、权益、统计、实时 Hub 和事件 Bus；这些服务在 Handler 里统一装配。M02M03

② 下发的任务结构

daemon 收到的 Task 里混着 Issue、Workspace、Project、workflow、Squad、Chat、Autopilot、QuickCreate 等字段。M04

③ Agent 的工具面

运行提示让 Agent 执行 multica issue get 和 multica issue comment list。协作状态是 Agent 作为副作用写回去的。M22

MW 接 SDK 的现状 ≠ 目标升级已兼容。MW 已经采用同源 SDK 执行入口，但应用服务仍然经由兼容客户端和头字段适配来访问引擎。W03W04 快照中 6 个引擎依赖包都存在，校验也匹配。W10W11 但抽取的 6 个文件里，dispatch.ts 和 permission/next.ts 与 SDK 基线逐字节相同，runner、server、bridge 和 package.json 不同（见 v0.1 的 vendor-comparison.json）。版本对齐要作为单独的闸门处理。
03 · 边界

用三类接口约定，明确复用与替换边界

近期接受 Multica 的对象和代码结构，避免为了“架构纯粹”先改写调度和存储。但调用方只认我们自己定义的语义，Multica 待在接口约定后面，作为首期实现。

左边是调用方，中间是长期稳定的自有接口约定，右边是首期实现。替换右边的实现，必须用真实场景和故障测试来证明，不能靠画图证明。

Team API · 团队应用接口

MW 团队入口用它建立和修改工作、生效计划、请求执行、答复批准、订阅变化。每条命令都带 actor、expectedRevision 和 commandId。版本冲突时不能静默覆盖，重复命令返回原来的结果。

协作工具 · 通用协作 API

team.read_work、team.submit_result、team.propose_handoff、team.request_decision：读工作、登记成果、提接续、请求决定。它们位于协作服务的接口边界，可以包装成 MCP 或 CLI。工具返回的是“提议结果或持久记录”，Agent 不能任意修改状态。

Provider 适配接口（执行器接口约定）

daemon 一侧：登记与领取（带所有权标识）、提交运行事件与结果（带 attempt/世代和 eventId）、能力声明。产品一侧：统一 Execute、事件、终态、取消、接续的语义，各 CLI 的协议仍然不同。接口统一不代表每种产品能力相同，不支持的能力要明确拒绝或降级。M05

上下文供给接口

按 actor、agent、run、用途、来源版本和预算装配依据，返回有权读取的依据及出处。缺失和冲突作为结构化结果返回，不编出一段“看起来完整”的答案。

四条候选路径：为什么默认第二条，什么情况下推翻

整体部署 Multica，直接用原 UI

得到：最快拿到原有产品体验，可作为参考基线。

代价：原 UI 无法验证 MW 融合和多种交互形态；还有品牌条件。

可作对照

复用后端和执行端，经 Provider 接入自有产品，增加应用接口

得到：尽早跑通端到端，保留已有的调度、回执和 CLI 接入机制；自有产品和第三方产品走同一种接入方式。

代价：继承工单模型、升级成本和许可条件。

内部原型默认路线

先抽出独立协作引擎包

得到：表面上边界更简洁。

代价：工单、提示、权限、通知与运行之间有真实耦合，抽取范围容易越扩越大。

拿到原型改动证据后再评估

参照机制，独立实现

得到：可以自主定义产品和技术边界。

代价：持久状态、重试、CLI 差异、恢复都要重新打磨。

授权或耦合无法接受时的备选

出现以下情况就推翻默认路线：原型显示改动持续侵入大量 Multica 产品模块，这时重新评估局部抽取；许可或授权条件无法接受，这时转向独立实现，而且不能复制受限实现来绕开许可。这不是长期供应商或商业合作的最终选型，技术原型的作用是为自研、共建或授权提供依据。
04 · 目标架构

产品组织工作，引擎持续执行

三层职责：交互层让人表达意图、看到结果；应用层定义业务规则，并把意图翻译成协作命令；协作层提供持久运行、接续、等待、回执等通用机制。看板、对话、IM 等不同界面可以复用同一个应用服务。协作层之下，执行端经 Provider 适配层调用完整的 Agent 产品，由产品负责“这一次运行怎样做完”。逻辑边界不要求拆成多个微服务。

端侧和云侧使用同一种接入模式（daemon → Provider → 产品入口），但执行环境、可用能力和权限不同，不是所有桌面能力都能在服务器上运行。所有连接都由客户端或执行端主动发起，服务器不需要入站访问员工电脑；服务端最多经已建立的连接发唤醒提示，任务由执行端领取后返回。这张图按物理机器画：员工电脑同时承担总图里的“人与客户端”和端侧“执行机”两个位置。■ 标出权威数据位置。

“测试 Agent”是一个角色和配置（含使用哪个 Provider），不等于某台主机。固定版在入队时按 Agent 当前绑定的 Runtime 记录，领取时还要求任务行上的 runtime 和 Agent 当前绑定一致，并检查在线新鲜度。M06M07 所以“同一个助手既能在我电脑上跑，也能在服务器上跑”，首期只能建成两个 Agent，或者显式改绑。按能力选择 Runtime 是后续需要验证的扩展。

部署克制：首期是一个协作后端、一个 PostgreSQL、必要的产物存储，桌面和服务器上各一个执行端，由执行端按需拉起 Agent 产品的 CLI / 无头入口。MW 无头执行依赖哪些桌面组件、进程怎样排布，属于待验证项。云端执行节点指的是自管服务器上的执行端，仓库里的 cloud runtime client 调用的是另一个服务，本轮尚未核实托管沙箱的完整供给实现。M20M21 如果要多实例部署后端，先核查跨实例通知、领导者任务和回收任务的并发安全，不能把副本数改成 3 就宣称高可用。
05 · 完整数据流

用一次交付走完全程：弱网重复待办修复 → 云端测试 → 负责人批准

负责人确认“先修复弱网场景下的重复待办，提醒功能延期”。研发电脑上由 Mobile Coder 修复，测试在服务器上执行，MobileWork 办公 Agent 并行准备发布材料，最后由负责人确认是否具备发布条件。三个执行者都由各自机器上的 daemon 经 Provider 适配层调用。重点看第 7–11 步：产出成果、提测、运行回执、领取测试是四件不同的事；人和 Agent 提测走同一个业务操作，唤醒只是提示，任务由执行端主动领取。这里只模拟发布，不影响任何真实业务系统。

06 · 对象与状态

先分清对象，才能分清状态：运行结束 ≠ 业务验收

工作项 ≠ Run ≠ 产品内部 session。下面是目标逻辑对象，不代表原型第一天就要新增同名数据库表。点击对象，查看它的含义、权威记录位置，以及首期和 Multica 的关系。

同一个测试步骤，两条状态线

测试 Agent 的 Run 可以“成功”，即正常跑完并交出报告，但报告显示测试不通过时，业务步骤仍然没有验收（T06）。目标状态名和 Multica 原有字段不是一一对应，映射表要在接口验证阶段固定。

只有一个运行状态写入者

应用提出命令，执行端报告事实，协作服务校验后更新。个人会话和团队工作不强行统一成同一个对象，二者通过明确的引用关联。

每次重试都保留原尝试

界面可以显示“同一步的第 2 次执行”，但底层不能覆盖第 1 次失败时的输入、证据和结果。

07 · Provider 适配

daemon 经统一 Provider 适配层，调用完整 Agent 产品的 CLI

在 Multica 执行端统一的 Backend 接口下，为每个产品实现一个 Provider 适配器：Mobile Coder 适配器调用 Mobile Coder CLI，MobileWork 适配器调用 MW 的无头办公任务入口，第三方适配器沿用或新增对 Codex、Claude Code 等 CLI 的接入。Mobile Coder 与 MobileWork 产品内部继续使用同源的 SDK harness；第三方产品保留自己的执行内核。统一的是执行语义，不是命令行格式。

目标设计示意。实线＝固定版已有或保留，虚线＝新增或待补齐。Multica 已有统一 Backend 接口与按 runtime/协议族构建后端的机制M05M25M26，本轮未核实已有可直接使用的 MC/MW 适配器。

统一语义，不统一协议

Execute、进度事件、终态、取消、接续是统一的语义；各 CLI 的参数、输出格式和会话标识各不相同，不强求都用同一个 --prompt 或一行 stdout，翻译由适配器负责。进程退出码只说明进程结束了，不等于业务成功：终态要看结构化结果、产品会话状态和产物清单。

端侧与云侧同一种接入

研发电脑和测试服务器上的 daemon 加载同样的适配器。区别在执行环境：装了哪些产品和版本、有没有桌面能力、持有哪些凭据和权限。执行端声明能力，协作服务按声明放置任务；桌面专有能力不能假定在服务器上可用。

Mobile Coder 适配器：首个落地候选

固定版 CLI 声明了 run、--session/--continue、--format json、--attach、--dirC02，run handler 经 SDK 引擎执行C04。这只说明它是接入候选：JSON 事件能否判定终态、取消是否收敛、审批能否拦截，都要在 G1 验证。不复制未审阅的配置，也不允许默认放行（YOLO）。

MobileWork 适配器：入口待补齐

调用的是产品的无头执行入口，不是自动化点击 GUI。入口可以复用产品现有服务，但必须保留 MW 的产品装配（办公能力、专家、插件），只套一层 SDK 壳不能冒充完整的 MW。现有 CLI 帮助只见服务、工作区、审批等命令W13，完整办公任务执行入口标为待补齐/待验证。

团队调用和个人使用要隔离

隔离什么

团队调用 MW 或 MC 时，使用独立的会话、工作目录和授权，不读取个人的私人历史和目录；个人使用照常进行，不强制经过协作调度。每个进程只能有一个管理者：个人链路由 MW 宿主管理W09，团队调用由执行端拉起，MW 界面最多展示连接状态，不能两边同时去启停同一个进程。

进程拓扑待验证

团队执行是复用产品已有的服务，还是由 CLI 拉起独立进程，无头运行又依赖哪些桌面组件，本轮都没有验证，不预设“两个独立 SDK 进程”。隔离也不等于完整的安全隔离：仍要约束工作目录、凭据和系统权限；产品会自动加载目录里的额外配置和记忆，需要在沙箱策略中验证。

运行中遇到 ask：转成持久决定，受控停止，再发起新尝试

长时间等待尽量放在业务步骤之间，不挂在某个不稳定的 CLI 进程里。在未确认停止之前，不能立即重启。跨进程持续挂起、等待实时答复可以作为后续扩展，首期不依赖它。

备选：daemon 直接接 SDK HTTP（协议验证路径，即 v0.1 方案）

在执行端实现一个 HTTP 后端，直接调用本机独立的 SDK 服务：创建 session、发 prompt、读事件、查询状态、abort。它适合验证 SDK 的会话与事件语义，或在产品入口补齐之前做对照；但它绕过了 Mobile Coder / MobileWork 的产品装配，所以不作为默认主路线。下面这些要求只针对这条路径，不能直接迁移成 CLI 路径已经具备的保证。

  • 同步 HTTP 200、异步接受 204、事件断开、出现一次 idle，都不能单独当作成功。S05S10
  • 路由的多进程分支没有直接处理 rejection，但 bridge 另有错误发布路径，不能只凭路由里的空 catch 就判定所有异常都被吞掉。S10S13
  • 取消走 session abort 入口，等本机执行收敛后再释放资源。S05S11
  • SDK 的本机 HMAC/Basic/PID 鉴权不能当作组织身份系统S04；本地服务鉴权依赖显式凭据配置，未配置密码时会放行，接入时必须固定配置。S14

产品运行内的子 Agent 仍由产品内部的 harness 管理。只有当它需要独立负责人、跨环境资源、单独审批或重试、产物交接时，才提升为协作服务里的一个步骤，避免同一个子任务被两层编排器同时管理。S07

08 · 可靠性

什么能自动恢复，什么必须先查清

可以借鉴 Spark 的集中协调、资源登记、任务领取和失败恢复。但 Agent 会修改外部系统、会等人决定，输出也不保证确定，所以“重复计算是安全的”这一前提不能套用到“重复执行所有 Agent 动作”。选一个场景，看每一层发生了什么、最后落在什么状态。

执行所有权：建议用单调递增的执行世代或等效凭据，在领取、续约、写回和释放时都做校验。它只能约束经过平台的写入；如果旧 Agent 仍然持有外部系统的长期凭据，平台无法凭世代号阻止它继续写外部系统。高风险动作必须经过受控工具出口，或依赖下游的幂等协议。首期先验证三件事：结果不丢、旧结果不推进、失败不乱重试，然后再扩大自动接管的范围。
09 · 可信上下文

先保证依据可用，再追求全面知识化

共享资料不等于每个 Agent 都读全部资料。要回答的是：这一步现在该用什么、凭什么认为它有效、谁有权读、结果能不能指回依据。

Manifest 至少包含

来源 ID、版本或哈希、确认状态、适用的工作、读取授权、装配时间、冲突或缺失项。汇总结果不是新的无条件权威事实，摘要要能追溯到原始依据。

读取时仍检查权限

快照固定的是内容版本，不是永久访问权。资料撤权后，新的读取和下游派生视图仍要授权检查；已经进入模型上下文的内容无法远程抹除，需要中止或重建受影响的后续运行。

图谱按效果再定

关系表或已有元数据就能表达“决定替代旧要求”“报告验证哪个版本”。本体和知识图谱不能保证数据本身正确、及时或已授权。要不要引入图数据库，看关系查询带来的收益是否超过维护成本。

不要低估，也不要高估现状。Multica 已有项目背景、评论增量，以及在工单和评论上的具体历史背景快照（带版本和大小预算）。M04M19M22 这不是“只有聊天记录”，但这套快照机制也不是通用的企业多源治理层。应先适配已有的供给能力，再补跨企业来源的治理。
怎样证明治理有价值：三组对照实验（待执行）

固定模型、任务和资料集，比较三种输入方式：①直接拼接或普通检索；②增加版本、状态和权限；③再加上明确的业务关系。比较的指标包括答案正确率、过期依据使用率、引用可核查率、权限隔离、输入 token 与耗时，以及人工整理成本。拿到对照数据之前，不承诺能提高多少比例。

10 · 编排

多 Agent 编排是策略，分布式协作是公共运行机制

mention 不是预设的 DAG

按固定版文档，@Agent 会在同一工单上拉起一次运行，但不会自动建立 A→B 依赖M11。交接给成员也不会启动 Agent；运行结束不会自动推进业务状态M12。条件接续靠持久唤醒规则实现M09M10。这几种触发来源不同，但最终都进入同一套授权、记录和执行机制。

蜂群只是其中一种策略

队长委派是通过提示和 mention 实现的协作策略M13。中央服务不需要变成一个全知的“总 Agent”。它可以调用规划策略，但必须能拒绝越权、条件不满足或超出预算的提议。组织策略变化时，不应重写运行存储和回执协议。首期只验证人工委派和条件接续，接入的 Agent 数量多不算完成标准。

11 · 融合

MobileWork 的双重身份：人使用的入口，也是被调用的办公 Agent

① 人使用的入口：个人用户照常创建会话、操作本地文件、使用专家；团队用户进入共同工作项，查看自己的任务、上下游依据、成果和待决定事项。② 被 daemon 调用的办公 Agent：团队计划里的办公类步骤（例如准备发布材料），由执行端经 MW 适配器调用产品的无头执行入口完成。团队入口可以是看板、对话或计划视图；“按角色默认工作视图”已记录为待细化功能，后续单独讨论。

两种身份共用同一个产品的装配和同源 SDK，但会话、工作目录和授权分开。进程怎样排布（共用已有服务还是独立进程）待验证。
