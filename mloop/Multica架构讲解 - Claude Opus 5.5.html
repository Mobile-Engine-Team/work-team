00 · OVERVIEW

Multica 把“派活”和“干活”拆在两边

先抓住服务端的两项核心职责：记账（工单、评论、每次执行的记录都在 PostgreSQL）和派单（把一次执行放进队列）。真正干活的是每台机器上的 daemon：它主动来领单，在本地调用 Claude Code、Codex 这类 AI 编程工具。Agent 干活时，又像一个普通成员一样用 multica 命令行回到工单上读评论、发评论、改状态。人和多个 Agent 的协作，就发生在同一张工单的时间线上。

粉色虚线是理解 Multica 的关键：Agent 本身就是平台 API 的一个调用者，回写走的路和人一样。点任一模块看细节。

洞察 1
工单（Issue）≠ 运行（Run）

工单是持续的工作；Run 是某个 Agent 的一次执行，代码里叫 task。一张工单可以有很多次 Run，Run 结束不代表工单完成。

洞察 2
队列就是数据库里的一张表

没有独立的消息队列。入队是 INSERT，领取是带条件的 UPDATE，WebSocket 只负责“叫醒”，掉线了还有轮询兜底。

洞察 3
多 Agent 协作＝评论 @ + 状态交接

本次读到的 Mention / 小队 / 工作流三条路径，都是由评论或状态变化触发 Run，交给中央 TaskService 入队，而不是由一个编排引擎预先排好流程：@ 谁就给谁排一次 Run；小队队长也只是“发一条 @ 评论”的 Agent；工作流靠“状态进入某列→换负责人→排 Run”。

阅读提示：下文用一个示例团队贯穿全篇：「官网」项目里，PM 林悦把工单 WEB-128 定价页增加年付切换并补 E2E 测试 交给「前端交付小队」。示例只用于串讲，不是运行记录；本文为静态源码分析：未启动 Multica，未通过 Multica 启动 Agent 或调用模型（本材料本身由 Claude 编写）。

01 · PRODUCT BEHAVIOR

一张工单的一生：8 幕看清人和 Agent 怎么接力

先不看代码，看用户能看到什么、数据库里多了什么。右侧“账本”是每一幕后数据库里新增或变化的行——Multica 的协作状态，全部能从这几类行里还原。

02 · CORE OBJECTS

核心对象：为什么要拆成这么多个

刚用 Multica 时容易混淆的几组概念，在代码里是严格分开的。拆开的理由都很实际：同一份配置要跑在不同机器上，同一件工作要被执行很多次。点击对象看字段和设计理由。

点一个对象

四组最容易混的概念

Issue vs Run：一件工作 vs 一次执行。
Agent vs Runtime：身份配置 vs 执行它的机器+工具。
Runtime vs Daemon：一台机器上的一个 daemon，会为每个工作区、每种工具各注册一个 Runtime。
Squad vs Agent：小队是“由队长分派”的负责人，不是新的 Agent。

为什么这样设计

Agent 只是配置（指令、模型、Skill、绑定哪个 Runtime、最大并发），不常驻进程；被触发时才生成一行 Run。这样同一个 Agent 可以同时处理多张工单，而每次执行都有独立的状态、会话、目录和费用记录。

真实怎么工作

入队时，Run 的 runtime_id 直接取自 Agent 当前绑定的 Runtime；没有绑定就拒绝入队。 负责人是多态的：assignee_type 可以是 member / agent / squad。

边界

一个 Agent 同一时刻只绑定一个 Runtime，Run 生成时就定了在哪台机器上跑。它不是“全团队机器池里自动挑一台空闲的”。换绑后，旧 Runtime 上排队的 Run 不会被新机器领取。

03 · SERVER vs EDGE

服务端记账，机器干活

Multica 的分工可以用一句话记住：服务端知道“该做什么、做到哪了”，执行机知道“怎么做、在哪做”。两边用一组很窄的接口交接：领单、开始、上报进度/消息、终态回执。

Go 服务端（+ PostgreSQL）

  • 工作区、成员、权限、Agent 配置、Skill、项目资源
  • 工单、评论、状态、收件箱、活动时间线
  • 任务队列：入队、领取事务、并发上限、去重与合并
  • 为每次领取签发任务令牌（mat_ 前缀）
  • 完成/失败落库、自动重试、超时与失联清扫
  • 两条 WebSocket：推给客户端的事件、连 daemon 的唤醒与 RPC
⇄领单 · 开始
进度 · 消息
终态回执

执行机上的 daemon

  • 发现本机 AI 编程工具，为每个工作区×工具注册 Runtime、发心跳
  • 本地并发槽位：先占槽再领单
  • 准备工作目录（新建 / 复用上次 / git worktree / 本地目录锁）
  • 写入 Agent 简报文件、拼 prompt、注入任务令牌
  • 通过适配层启动 CLI，收流式事件，监控卡死
  • 终态回执先写本地文件，再上报，失败可重放
部署形态 源码

自托管 compose 只有三个服务：postgres（pgvector/pg17 镜像）、backend（Go）、frontend（Next.js）。 没有独立的消息队列或调度服务；Redis 是可选的，多实例时才用于跨实例事件和缓存。 daemon 不在服务端部署，它装在每台执行机上（桌面端也会托管一个）。

数据边界 文档

代码目录、工具自己的登录凭据留在执行机，服务端不替本地执行命令，也不上传整个目录。但服务端保存评论、执行记录和 Agent 主动写回的内容；Agent 的 custom_env 和 MCP 配置存在服务端，执行时下发。

为什么这样设计：AI 编程工具需要真实的仓库、依赖、云 CLI 和登录态，这些在用户机器上最完整。让机器“主动来领”而不是服务端“推过去执行”，执行机就不需要暴露入口，内网机器也能接入；服务端则可以保持无状态、只靠数据库协调。
边界：这套分工默认把执行机当作可信环境，隔离边界交给部署方（专用系统用户、容器或虚拟机，见第 08 节）。如果把它搬到办公场景，执行机上的“工具”就不再是编程 CLI，数据边界也要重新划。

Run 的状态机

点击状态看它什么时候进入、怎么超时。注意：自动重试不是把 failed 改回 queued，而是插入一行新的 Run（attempt+1，parent_task_id 指向原行），所以每次尝试都留痕。

点击一个状态

本次读到的关键状态变化都是带前置条件的 UPDATE：比如完成只对 status='running' 的行生效，领取只对 status='queued' 生效。旧请求晚到时更新 0 行，自然失效。

看源码：领取 SQL 的核心条件（agent.sql）
-- ClaimAgentTask（节选）
UPDATE agent_task_queue
SET status = 'dispatched', dispatched_at = now(),
    prepare_lease_expires_at = now() + make_interval(secs => @prepare_lease_secs)
WHERE id = (
  SELECT atq.id FROM agent_task_queue atq
  WHERE atq.agent_id = @agent_id AND atq.runtime_id = @runtime_id
    AND atq.status = 'queued'
    AND EXISTS (... a.runtime_id = atq.runtime_id   -- 换绑后旧行不可领
                 AND r.status = 'online' AND 心跳足够新 ...)
    AND NOT EXISTS (... 同一 agent 在同一 issue 上已有
                     dispatched/running/waiting_local_directory 的 Run ...)
  ORDER BY atq.priority DESC, atq.created_at, atq.id
  LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING *;

这一条语句同时保证了：只领本 Runtime 的、Runtime 在线、同一 Agent 对同一工单串行、不同 Agent 对同一工单可以并行、多个领取者互不阻塞。

看源码：WS 优先领取，结果不确定时先停一拍再走 HTTP（wsrpc.go）
if errors.Is(err, errWSRPCUncertain) {
    // The WS claim may have committed server-side; claiming the same
    // free slots again over HTTP immediately would double-claim. Skip
    // this cycle, then force one HTTP batch claim after the server-side
    // execution budget plus response grace has elapsed.
    d.wsClaimHTTPFallbackAfter.Store(time.Now().Add(delay).UnixNano())
    return claimTasksResult{}, nil
}

“没发出去”可以立刻改走 HTTP；“发出去了但没收到回复”不能，因为服务端可能已经领取成功。后者交给服务端的“已派发但未开始”回收机制。

05 · CONTEXT

上下文：当前指令直接给，历史背景按需读

以普通的“工单指派 / 评论触发”路径为例（对话、自动化等其他入口本次未展开）：Multica 不会把工单描述和整条评论线程都拼进 prompt。本轮要处理的内容直接内联——触发评论原文、并入本轮的其他评论原文、工作流交接说明、续接时的变化提示；历史背景则交给 Agent 用命令自己去读。再加上写在工作目录里的稳定“岗位说明”，一共四层。点击左侧四层，右侧看示意 prompt。

示例据 prompt.go 中真实模板改写缩短，ID 用示例值；实际文本为英文。

为什么这样设计

工单可能有上百条评论。全量塞进去既贵又会淹没本轮指令。稳定内容放进工作目录里的简报文件（Claude Code 读 CLAUDE.md，Codex 读 AGENTS.md），每轮变化的内容追加在 prompt 末尾，这样续接会话时前缀能命中模型的提示缓存。

真实怎么工作

续接同一会话时，服务端比较“上次 Run 开始时的工单快照”和现在，告诉 Agent 哪些字段变了、之后新增了几条评论；比不了就不报，让 Agent 照常去读。会话只在同一 Agent、同一工单、同一 Runtime 上续接。

边界

本次读到的主链路证明的是“共享记录 + 快照差异 + 引用指针”。至于是否另有企业级语义治理（统一事实库、结论版本、按权限检索、本体图谱），本次没有核验，不能据此断言有或没有。在这条主链路里，历史读没读、读得对不对，靠 prompt 里的工作规范约束 Agent；系统记录的是“哪些评论投递进了本轮”。

看源码：会话只在同一 Runtime 上续接（handler/daemon.go）
// Non-rerun follow-up on the same issue: resume the most recent

// context across turns.

会话文件（如 Claude/Codex 的对话记录）存在执行机本地，换机器就读不到，所以只在同一 Runtime 上续接；工作目录指针则照常给出，daemon 找不到时会新建。

06 · MULTI-AGENT

多 Agent 怎样组织：三种机制，同一条队列

Multica 有三种让多个 Agent 协作的方式。它们决定的是“谁下一步被排一次 Run”，底层执行路径完全一样：入队 → daemon 领取 → 执行 → 回写评论。

规则

评论里用 mention 链接 @ 了哪个 Agent，就给它排一次 Run。不同 Agent 可同时处理同一工单；同一 Agent 在同一工单上严格串行。

合并而不是丢弃

某 Agent 在这张工单上已有一个还没被领走的 Run 时，新评论会并进去：新评论成为触发评论，旧的列为“也要处理”。已经开始执行的，新评论登记为待投递输入。

边界

纯文本 “@名字” 不会触发；插件代发的评论也不会触发 @。 多个 Agent 同时改同一个 Git 仓库资源时，默认各用 worktree/分支，合并由人决定；本地目录原地模式下则排队串行。

工单指派给小队后，只给队长排一次 Run。队长被领取时，服务端在它的指令后面追加三段：硬编码的「小队工作规范」、带可复制 mention 链接的「花名册」、用户写的「小队指令」。规范要求队长：读工单 → 用 @ 派活 → 记录评估 multica squad activity → 派完就停，不亲自动手。

小测：哪条评论会再次唤醒队长？

选左侧一条评论。
要分清两层：“队长怎么分派”是写在 prompt 里的策略，由 LLM 执行，系统并不能阻止队长自己写代码；“队长什么时候被叫醒、会不会重复入队”才是代码里的触发规则（评论路由、自触发抑制、待处理去重）。 小队不会合成新 Agent，也不提高并发。

规则

工作流给项目的每一列配置“进入时交给谁”：不交接 / 交给 Agent / 交给成员。普通的状态变更进入某列时，负责人被改写为该列处理人；若是 Agent，就用这一步的说明作为交接说明排一次 Run。

谁推动下一步

Run 结束不会自动推进状态。由负责这一步的人或 Agent 改状态；Agent 改状态同样触发下一列的交接。“完成后进入/打回到哪一列”只是写给 Agent 的说明。

防串步

每个由交接启动的 Run 记着自己负责的步骤（workflow_step，重试时继承）。若工单已被别人移走，这个 Run 再改状态会被拒绝，避免覆盖人的决定。

边界：这是“状态驱动的负责人交接”：每张工单同一时刻只有一个负责人，下一步走向由“完成后进入 / 打回时退回到”等配置写给 Agent，再由 Agent 或人改状态来触发。本次没有看到它被用作任意节点调度的 DAG 引擎；更复杂的跳转能力以官方文档和代码为准。
07 · RECOVERY

出故障时谁来兜底

分布式执行的难点不在“跑起来”，而在“半路出事以后数据库里的状态还对不对”。从本次读到的主链路看，Multica 的做法是：领取、准备、执行这些可能中断的环节用租约/心跳判断死活，关键状态变更用条件更新防止旧请求覆盖新状态。选一个故障看过程。

自动重试的范围 源码
失败原因最多执行次数
运行时离线 / daemon 重启回收 / 平台超时 / Codex 停滞 / Skill 包下载失败默认 2 次
模型服务网络中断 provider_network3 次，最后一次约延迟 5 秒
鉴权、额度、配置、模型不可用、上下文溢出等不自动重试

自动化的“仅运行”模式不自动重试。

重试 Run 继承什么 源码
  • 同一个 Runtime（复制 runtime_id），不会换到别的机器
  • 同一个工作目录（复制 work_dir），已写的文件尽量保留
  • 会话一般保留；Codex 停滞类失败会清掉会话、强制新会话
  • 触发评论、归因（谁发起、谁负责）、工作流步骤
不要误读成“自动无缝接管”：①重试固定在原 Runtime，机器长期不回来，Run 最终失败，需要人换绑 Agent 后重新触发；②会话和目录都在执行机本地，换机器只能从新会话、新目录开始，靠工单记录接续；③平台的幂等只覆盖它自己的状态行和评论投递回执。Agent 在一次被中断的 Run 里已经做过的外部动作（git push、开 PR、调第三方 API、发消息），重试时可能再做一遍，平台无法撤销或去重。
08 · PERMISSIONS

权限：平台管身份，机器隔离另设边界

Multica 的权限要分两层看：Agent 以谁的身份调用平台 API，这一层管得很细；Agent 进程在机器上能碰到什么，官方把边界定在 daemon 的操作系统用户上，默认不提供文件系统沙箱，建议用专用用户、容器或虚拟机另设边界。

第一层 · 平台身份（服务端强制）源码

  • 每次领取签发一个 mat_ 任务令牌，daemon 作为 MULTICA_TOKEN 注入 Agent 进程；daemon 拒绝用自己的凭据兜底。
  • 服务端校验令牌后，用令牌绑定的（用户、Agent、任务、工作区）覆盖请求头，客户端伪造的 X-Agent-ID 无效；工作区不匹配直接拒绝；仅限人类的接口拒绝任务令牌。
  • 每个 Run 记录发起人和问责人（originator / accountable）；找不到明确的人时可配置为拒绝入队。
  • 成员能否 @ 某个 Agent 或小队，取决于他有没有权运行这个 Agent（小队看队长）。

第二层 · 执行机（默认不提供文件系统沙箱，边界是 OS 用户）文档

  • 官方安全模型把权限边界定在 daemon 所属的操作系统用户：默认路径下，Run 能做该用户能做的事，例如读 SSH 私钥、改 shell 配置、访问网络。Multica 不保证文件系统沙箱。
  • 无人值守执行，审批被自动应答：Claude Code 以 --permission-mode bypassPermissions 启动，Codex 默认 danger-full-access。例外：Windows 上若显式开启 Codex 原生沙箱，Multica 会尊重该设置，保留 workspace-write。
  • 平台自带的隔离主要是“便利性”的：Run 通常有自己的工作目录（但本地目录原地模式共享真实目录、靠路径锁串行；同一 Agent 在同一工单上的后续 Run 会复用上次目录）、独立的 Codex 状态目录、绑定到 Run 的 API 令牌。
  • 官方建议把边界放在 daemon 外面：专用系统用户 → 容器 → 虚拟机。

插件 · 两道权限取交集文档

  • 插件界面跑在 sandbox="allow-scripts" 的 iframe 里；每次调用 = 管理员授予的 scope ∩ 当前用户本来就能做的事。
  • 插件代发的评论署名为用户，且不触发 @ 派发——插件不能顺手启动 Agent。
为什么默认不做文件系统沙箱：官方的理由是，Agent 要装依赖、跑构建、用 gh/aws/kubectl，不完整的沙箱会以难以排查的方式破坏这些工作，又挡不住“读到凭据后通过网络发出去”。 推断这对开发者团队是合理取舍；面向非技术员工、涉及企业数据的产品，执行层隔离必须是产品的一部分，而不是部署建议。
09 · EXTENSION

扩展：三个插口

① 执行器适配层 源码

所有 AI 工具实现同一个接口：Execute(ctx, prompt, opts) → Session。Session 吐出统一的 7 类消息（文本、思考、工具调用、工具结果、状态、错误、日志），最后给一个 Result（状态、输出、会话 ID、按模型的用量）。

接入协议各不相同：Claude 走 stream-json，Codex 走 app-server，DSH 走自有版本化 JSONL，多家走 ACP。

② Skill 与 MCP 文档

Skill 是挂在 Agent 上的“这类工作怎么做”的说明包，领取时随任务下发，由 daemon 写入本次执行环境；下载失败属于可自动重试的故障。

MCP 配置挂在 Agent 上；另外每个 Run 会按发起人生成一份“已连接应用”叠加配置，同一个 Agent 被不同人触发，能用的外部应用可能不同。

③ 插件 源码

插件和宿主只有三种关系：Action（插件调平台）、Hook（平台调插件，可由界面、手动、Agent、事件、定时触发，定时最短 5 分钟）、Resource（静态贡献，如 Skill 文本）。界面挂在工单面板、侧栏或弹窗三个固定位置；scope 是封闭列表。

10 · IMPLICATIONS

对类 Loop 产品的启示

建议本节是基于公开 Multica 源码的判断，不代表 Loop 的实现，也不能替代对 Loop 私有改造的核实。是否采纳由你决定。

值得借鉴的结构
  • 工作项与执行记录分离：一件事多次执行、多人多 Agent 接力，天然可追溯，费用和失败也能按次统计。
  • 数据库即队列 + 条件更新：组件少、状态唯一，重复回执、晚到请求都靠前置条件自然失效。
  • 执行端主动领单：数据和凭据留在执行机，内网也能接入。
  • Agent 是平台 API 的普通调用者：权限、审计、通知、实时刷新全部复用人的那一套。
  • 协作即评论：路由信号（@）和工作记录是同一个东西，人随时可以插话、纠偏。
  • 当前指令内联 + 历史按需读取 + 差异提示：控制成本，同时不丢新输入。
需要自己补的部分
  • 执行隔离：Multica 默认交给部署方（专用用户/容器/虚拟机）；办公场景数据更敏感，可能需要产品内置。
  • 上下文治理：本次主链路只看到工单内的共享记录、快照差异与引用；团队级知识沉淀、结论版本、按权限检索是否存在需另行核验，类 Loop 产品要自己想清楚。
  • 编排的可控性：小队分派靠 LLM 遵守 prompt，结果不可预测时只能靠人看时间线纠正。
  • 跨机接续：会话和目录绑定机器，换机等于冷启动。
  • 外部副作用：重试可能重复执行外部动作，需要业务侧幂等或人工确认点。
  • 非编程执行器：工作目录、分支、worktree 等概念都假设产出是代码。
