# 新会话任务书 · 将冻结 Demo V2 迁移到 DSH + Multica

请用 Codex、GPT-6.2 Astra、high 推理强度负责实现、集成与复验。目标是在现有产品仓交付一个能从 Finder 双击启动的通用 Mac .app，使用户在与冻结 V2 相同的条件下看到相同的界面，沿相同路径完成操作，并得到相同的业务结果。按[用户裁决](demo-v2-baseline/06-已有用户与裁决.md#d-01)处理例外。请持续做到可交给我亲自验收。

## 从哪里开始

1. 研究仓为 `AI_product_research`。先读根 AGENTS.md、project/current.md，再读[基线入口](demo-v2-baseline/README.md)、第 06 章、[覆盖表](demo-v2-baseline/coverage.md)和[复验步骤](demo-v2-baseline/replay.md)。以六章条目和[控件反查](demo-v2-baseline/controls.md)界定完整产品，包括二级入口、菜单、弹窗、个人/团队两区、角色、空态、失败与恢复。只在有疑义时沿对应条目查冻结源码、恢复清单或打开原版复验。
2. 实现在研究仓下的独立 Git 仓 `products/dsh-team-workbench`。先检查内外两仓的工作区状态。基线、截图和本地冻结依赖可能只存在于当前工作副本；如另建 worktree，先确认新会话能读取同一套材料并运行相同入口。保留现有修改、原用户资料和原演示现场。使用隔离的测试数据库、上传目录、执行端和账号。
3. 从[产品 README](../README.md)与[首批验收记录](acceptance.md)启动当前迁移版，跑一次现状检查。已有 A/B 启动壳、A1–A8、浏览器测试和确定性执行器提供回归起点。对照冻结版找出缺失行为、额外入口、视觉差异与不可达代码。根据实际差距制定短计划，然后直接开始修改。

## 按完整旅程实施

- 先打通启动、注册登录、同机换号隔离和 A/B 协作。以三条旅程校准实现深度：新建工作区的字段、三种关闭、失败和成功落点；个人/团队智能体的执行端选择、换端后的模型及共享权限；创建任务、分派、触发执行、评论和另一成员的通知。随后完成项目、讨论结论、蓝图发布与推进、私人工作台、依据、固定视图等其余可达旅程。可按依赖调整顺序。
- 先比较冻结实现与产品仓已有的组件、样式、业务服务和契约。可复用且允许复用的部分优先沿用，再适配 DSH Client、Host 和 Multica。产品正常入口要走实际装配和业务写入。测试夹具用于构造在线/离线、延迟、失败或已完成回答等可控条件。检查交付的 .app 如何启动和定位自己的依赖，避免靠打开原版页面、开发者手动拼接端口或给每个账号单独生成一个壳完成演示。
- 为每个基线编号维护可续接的差异记录。最少记下运行条件、原版依据、迁移版观察、关联修改/测试及当前判定；多分支条目分开记。按旅程小批完成实现、定向测试和相邻路径回归。上下文压缩或交接前更新当前进度、可重放命令和下一处未解决差异。
- 授权使用 **Codex 子代理**做有明确边界的工作，例如并行核查独立模块、复核截图、写回归测试，或对已完成批次做独立复验。主代理负责共享契约、集成和实际运行。委托复验时提供冻结证据、待测构建和测试身份，让复核者从真实入口独立操作。开发与审查均用 Codex；DSH 是目标产品运行架构。

## 按已确认的取舍验收

- 用**同一个通用 .app**做两种测试。其一，A 在同一资料中留下私人草稿并退出，再登录 B。B 应看到自己的工作区和数据，获授权的团队任务仍可见，A 的草稿、对话和固定视图均不可见。其二，同一 .app 启动两个隔离测试实例，让 A 创建任务并分派给 B，让 B 打开通知、评论并交付，由 A 核对结果。两项分别留证。
- 旧数据可尝试带入，成本高即可从新账号按基线重建相同条件。走旧现场时按 D-02～D-06 核对登录、归属、链接、附件、未读和在途执行，防止静默重跑。D-07 已批准两项变化：任务筛选重置后留在任务页；新建任务上传附件失败后可重试、移除或取消。其余用户可见差异先按基线修正。确需新取舍时列出条目、证据和影响，由我裁决。
- D-08 暂缓。实现相关产品路径，并尽量用本地受控条件验证请求、状态转换、取消及归属。真实付费模型和外部 SSH 联通留待另行授权，报告中标清仍未验证的部分。不得使用真实用户凭据或对外发布。

## 用什么证明完成

1. 在同一构建上复跑产品构建、类型检查、自动测试及浏览器回归。当前产品命令为 `pnpm build`、`pnpm check:types`、`pnpm test`、`pnpm test:browser`。执行前查清本机服务归属。针对实际发现、已有测试捕捉不到的差异增加回归用例。
2. 从交付的原生 .app 验启动和关键旅程。按原版的 1180×810 CSS 像素、缩放、主题及语言对齐原版与迁移版。对照关键截图，检查文字、布局、控件、焦点、键盘、加载和错误状态。原生壳、菜单、关闭与重开单测。时间、标识与模型正文等自然变化按基线比语义。证据应能定位到具体构建、测试身份和条目。
3. 对涉及写入、权限或异步执行的条目，同时查 UI、持久化业务结果及另一用户所见。例如任务创建成功、业务“进行中”、执行“排队中”、实际被领取、完成或取消分别留证。主动覆盖同机换号、刷新重开、离线、重复提交、失败重试与并发；对原版实际可达性仍不清楚的条目标注条件和依据。
4. 提交给我一个本机可启动的 .app 路径，以及一个验收入口，包含复验命令、合成账号准备步骤、差异表、关键画面对照、测试结果和待裁决项。将已对齐、已批准变更、真实外部条件暂缓、证据不足及仍有差异分别列出。先修复可在当前授权内解决的差异；存在未解决的核心路径时如实报告，不宣告整体验收通过。最终的用户体验验收由我完成。
